# game-translation

[Скилл Claude Code](https://docs.claude.com/en/docs/claude-code/skills) для перевода/локализации
сборки игры. Он не заменяет собственный пайплайн перевода проекта — это чек-лист, который не даёт
агенту отчитаться «переведено», когда закончился только основной проход, а исходный язык на деле ещё
остался в слое, который основной проход не проверяет.

## Зачем это нужно

Сборка игры прячет текст не в одном месте: таблица строк, скомпилированный скрипт, сериализованный
блок данных и текстура с текстом, нарисованным прямо в пикселях, могут нести текст в одной и той же
сборке одновременно. Пайплайн, который аккуратно обрабатывает первое из этого и завершается без ошибок,
честно отчитывается об успехе — а сборка всё равно может уйти в релиз с непереведённым текстом в
остальных трёх слоях, потому что их никто не проверял. Этот скилл — та самая проверка, которая
обходит все четыре слоя до того, как будет сказано «готово», плюс дисциплина перевода и рецепты
починки по слоям, которые обычно требуются по итогам проверки.

Он написан после сессии, где Unity/IL2CPP-сборка переводилась вручную — строки доставались из
сериализованных бандлов, патчились скомпилированные в бинарник строковые литералы, перерисовывался
текст, запечённый в текстуры интерфейса, переключались флаги разблокировки, заданные данными, —
потому что более ранний автоматический проход оставил примерно 40% текста игры на исходном языке, в
слоях, куда проверка первого прохода вообще не заглядывала. Скилл обобщает метод той сессии и её
конкретные промахи в чек-лист, не привязанный к конкретному контейнеру.

## Что входит

| Шаг | Содержание |
| --- | --- |
| 0 | Сначала использовать существующий автоматический пайплайн, если он есть в проекте; к ручным шагам переходить только там, где он сам сообщил, что не справился. |
| 1 | Где прячется текст, по слоям: таблицы строк, скомпилированные/байт-код скрипты, сериализованные блоки данных, строковые литералы уровня кода, текст, запечённый в картинки — и почему наивная проверка пропускает каждый из них. |
| 2 | Перевод через LLM батчами: вызовы в JSON-режиме, глоссарий, лимиты длины на строку, проверка ответов, размышления только на повторном проходе, и как отличить региональную блокировку от отказа по содержимому. |
| 3 | Применение переводов: переписывание индексов/смещений вместо правки байтов на месте, синхронизация любого бокового индекса (каталог пакета, каталог бандла, таблица строковых литералов) с тем, что он индексирует, и три конкретные ошибки, которые незаметно теряют или портят строки. |
| 4 | Контроль: повторный прогон проверки из шага 1 по реально собранному результату, а не по исходным ассетам, и отношение к любому ненулевому счётчику как к незаконченной работе, а не заметке на будущее. |
| 5 | Проверка сборки запуском, в рамках разумного — обход всех экранов интерфейса, которых коснулся перевод, без того чтобы агент сам доигрывал до контента, который ему не стоит генерировать или описывать. |
| 6 | Отчёт: что переведено (со счётчиком проверки), что осознанно не тронуто, что не проверено. |

## Установка

Положить папку туда, откуда харнес читает пользовательские скиллы, и перезапустить, либо дождаться,
если каталог отслеживается автоматически:

```
cp -r game-translation <skills-root>/game-translation
```

`<skills-root>` — это `~/.claude/skills` для Claude Code, а для профиля DSH (`@deepseek-ai/dsh`) —
тот корень пользовательских скиллов, который магазин скиллов сообщает для цели `user-dsh`.

## Рамки применения

Это чек-лист для агента, не готовый к запуску скрипт — проверки и рецепты описаны прозой, потому что
контейнеры, к которым они применяются (таблицы строк движка, скомпилированные скрипты, бандлы
ассетов, текстуры), слишком по-разному устроены в разных проектах, чтобы один фиксированный скрипт
покрыл их все. Проект с собственным автоматическим пайплайном (определение движка → извлечение →
перевод → применение → проверка целостности → пересборка) должен продолжать им пользоваться; этот
скилл закрывает разрыв между отчётом такого пайплайна и реально законченным переводом.

## Почему это устроено именно так

Контроль из шага 4 — единственное правило, ради которого существует всё остальное в скилле:
повторная проверка именно по собранному результату, а не по исходным ассетам, — это то, что ловит
перевод, который был верным в промежуточном файле, но так и не попал в пакет, или шаг пересборки,
который незаметно откатил изменение. Всё, что стоит перед этим шагом (где прячется текст, как его
переводить, как применять без порчи бокового индекса), существует для того, чтобы этой финальной
проверке оставалось находить как можно меньше реальных промахов.
